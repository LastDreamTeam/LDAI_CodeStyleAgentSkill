## 流程：规范与CLI回归

前提：Python3.10+、Git，当前目录为本仓库根；CI另提供Node语法检查。配置/状态及Git测试使用临时目录，不修改真实用户黑名单。

1. 运行 `python -B -m unittest discover -s tests -v`，分别核提交身份、每日节流、健康门禁、环境变量策略及既有历史/交互工具。
2. 运行 `node --check skills/ld-codestyle-online/assets/question.js` 和 `git diff --check`。
3. 推送后核准确分支SHA及CI矩阵；合并后对准确合并版本再检查。不能将分支结果冒称合并版本已验，不能将模拟registry/更新后端称为全部宿主实机通过。
4. 发版包仅从准确Git树生成，完整技能含许可、版本和全部脚本；解包后运行维护、身份及项目策略CLI，校验文件摘要和来源提交。

已核环境边界：2026-11-11，0.5.0开发回归时，本机3项安装链接测试因Windows `WinError 1314`（无符号链接特权）失败；同日未修改主线 `0d8b7eb` 的相同3项复现同一错误。不得把它算通过，也不得靠修改全机权限或跳过保护来掩盖。其他平台/Windows runner结果需从对应CI实际回读；此记录不预填发版成功。

2026-11-19（0.6.1）：上述3项改为在当前用户无法创建目录符号链接时整类按平台跳过，并在跳过原因中写出异常类型与 WinError；有权限的环境（含 CI 的 Windows/POSIX runner）照常执行。跳过不等于本机安装链接已验证：本机 DSH/Codex 实际使用的是目录联接（junction），需另行核对安装入口与版本。同轮还修正了测试辅助子进程在 cp936 代码页下的解码噪声来源说明（子进程失败输出非 UTF-8 时 reader 线程报错，属失败附带现象，不是独立缺陷）。

## 流程：依赖方采用健康门禁

- 在技能相关任务入口按安全空档执行 `sync --idle`，只要版本落后或更新关闭，健康必须标脏；同日重复不重新联网检查。
- 相关推送前使用 `health --require-healthy --min-version "<依赖方要求的版本>"`；退出3代表健康不满足，4代表版本不满足。仅运行普通`health`返回0不能当作通过门禁。
- 过期、损坏或中断状态必须保留未知/失败，不把缓存曾健康当成永远健康；任务无关时不触发维护。

## 流程：项目记忆默认与明确排除

- 用 `project_memory.py show --project-root "<真实项目根>"` 确认默认启用；此查询不应写业务文件或联网。
- 只有主人明确要求才调用exclude/include。默认候选输出必须 `persisted=false`，当前`enabled`不应被候选值冒充。
- Windows持久化只访问指定用户环境变量，写后回读；其他系统按实际宿主环境入口保存后再查询，不能说建议已生效。测试坏JSON、别的根、兄弟前缀、路径别名和旧继承环境，排除不删除共享文件或禁用身份规则。
- 本仓库真实用户环境未被测试排除；自动测试用隔离数据/registry替身。各引擎实际资产导入和跨设备共享效果仍需相应项目验收。

## 流程：默认交付范围与最终求助（Issue #21）

1. 运行 `python -B -m unittest discover -s tests -p test_push_scope.py -v`，验证精确候选保全源码、正式测试、资源及对应元数据；干净clone能执行正式夹具测试，一次性探测/日志和人工dirty内容留在原地且字节不变。
2. 缺失必要 `.meta` 的负例必须因该文件缺失而失败，不能把任意退出1算验证成功；最终树删掉副产物的历史案例仍应在全部待推送提交里发现前一版本。
3. 问询模板必须兼容既有QuestionSession，两种实质方案与纯自由文本均能回传；业务方向未定时超时不自动选推荐、不签发推送许可。
4. 语义复核入口：已尽合理努力核查才求助、重大业务影响、支持异步则途中询问并继续独立工作、无可用询问功能则暂停同会话提问，超时/无并行任务保留待决；只有阻塞式能力不能被误写成无询问能力，收尾仅汇总而不延迟首次求助。

2026-11-11开发验证：新增9项定向验收通过，包含3个真实临时Git流程；本机全套150项中145通过、2项按平台跳过，3项仍为上方已记录的安装符号链接权限限制。测试只证明这些合成依赖与既有问询协议的行为，不代表Unity编译、实际业务或所有外部Agent均已遵守；不新增自动文件分类、Git门禁或宿主异步功能。发布后的准确提交与CI结果以Release回执为准。

## Go 服务端与 Windows 桌面客户端接手试点（#20）

2026-11-18，另一位未参与编写规则的 AI 接手者仅得到两个业务仓库的入口。它从两份根 README 的共享资料导航找到客户端 `Agentic/USER.md` 的当前决定（设备可独立连接，使用聊天需要操作者登录），从服务端 `Agentic/MEMORY.md` 识别已退役的旧聊天桥接方案，并从两仓 `Agentic/DEBUG.md` 找到启动入口。旧资料保留为历史，执行当前决定。可访问这两个仓库的维护者可按下列步骤复跑。

1. Windows 上检出客户端 `728ea7caef641dc3d1d60375fae65a1b60adb0b9`、服务端 `2f40f1e2eb8c20ddb4b9ce334ae94cf2cb087c74`。从各仓库的 `cmd/nodeagent-client` 和 `cmd/nodeagent-server` 用 Go 构建产品。两份 EXE 的 `go version -m` 均指向上述提交，工作树标记为干净。
2. 服务端用独占回环端口和新状态目录启动。客户端用另一新数据目录与临时配置，指向该本地 HTTPS 服务并关闭自动连接、开机启动、自动更新、执行与桥接，使用中继模式。按客户端 DEBUG 的 `--headless` 入口启动真实 Windows EXE，再在**有窗口的浏览器**打开它提供的本地桌面面板。这个参数只用于避免自动开窗和托盘。会话链接、状态文件和配置仅留在授权环境。
3. 从“尚未连接”点“一键连接”，等面板显示“此电脑已连接”。打开 Chat，不登录。应看到“登录后使用聊天”；在此次服务端状态中核同一个测试节点仍有新心跳，任务数为零。
4. 两次使用全新目录和独立端口复跑，均观察到连接状态变化、聊天登录提示和同节点后续心跳，未执行任务。没有替身服务或测试程序代替产品面板。结论限于此连接与登录边界：未测托盘、UAC、真实账号登录、消息收发或生产部署。接手者是独立 AI，未进行人类可用性访谈。复核结果见 [Issue #20](https://github.com/LastDreamTeam/LDAI_CodeStyleAgentSkill/issues/20)。
