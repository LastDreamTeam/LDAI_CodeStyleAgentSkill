# 区域 SQLite 历史与有限摘要

## 两层职责

参考 [Hermes Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory) 的“有限常驻记忆 + 按需历史检索”。不读取其私有 `state.db`，不复制全量聊天归档；Hermes 的额度满时拒写也不等于自动无损压缩。

- `Agentic/USER.md`、`MEMORY.md`、`DEBUG.md` 是有硬上限的当前摘要；README继续承担地图和业务说明，不作为第四份历史流水。
- 同目录 `history.sqlite3` 保存**精选完整历史**：属于所属README声明责任范围的用户原话，以及已验证的bug修复、踩坑与避坑经验。不是全部项目活动或全部会话的逐字档案，不捕获其他区域或Bot私人记忆。
- 所属README明确数据库真实入口、scope标识、负责路径/排除项和检索工具。同名scope不能代替实际归属判断；跨层联动上提到共同责任层，独立局部下放，不为每个函数再建库。
- 开工读当前摘要；需要原意、旧修复、例外或证据时，先按关键词/ID检索索引，再读命中完整条目。**不全库注入、不无限分卷**：不把库或全部导出自动注入会话，不靠无限Markdown分卷、完整索引列表或拆假区域绕额度。

## 入库选择与完整性

`user`：保留真实原话中与本责任区有关的完整语义段落、来源、原日期（未知明写）、条件/否定/例外、确认或探索状态。跨话题只选相关段，明确摘录范围；脱敏位置标占位，不改写摘要后冒充原话。一次性无持续价值的工单不默认入库；重要需求演进和被替代原要求可保存。不以数据库里出现旧要求生成新授权。

`debug`：仅收已有证据的成功修复、已验证切片或确证的避坑结论，正文包含现象/触发、已知历史、根因与不确定部分、有效步骤、原理、适用版本/环境、真实验证结果、防复发条件及未覆盖范围。必要失败经验可作为已证实坑点保留；不收全量试错、未验证补丁、猜测或无价值工具输出。源码/日志附件可以引用，但完整因果不能只剩一个可能失效的链接。

每条使用稳定ID、`kind`、`scope`、`title`、完整`content`、`source`、`occurred_at`、`related_paths`、`relevance`、`status`、`evidence`、`supersedes`、`redacted`。字段示例见 `templates/history-user.example.json` 与 `history-debug.example.json`，只用合成数据，不当实际证据。身份与公开脱敏继承目标仓库规则，不能在数据库/导出里偷偷回填公开提交已省略的私有身份。

同ID同内容幂等；同ID异文拒绝。修订用新ID和`supersedes`串起原文，不UPDATE覆盖；旧记录永不自动视为当前要求。SQLite事务、SHA-256和完整性检查只证明结构/字节一致，不证明来源、相关性或结论真实。`--reviewed`是调用者已完成来源、scope、保真和隐私核验的声明，不是机器或人类审批证明。

## 日期与类型：独立SQL列和筛选

`records`除`id/payload/sha256`外，使用独立的`kind TEXT NOT NULL`及`occurred_at TEXT`列，不只埋在JSON中。`kind`只允许`user/debug`；日期列保存来源日期或带时区时间原写法，原始payload及其hash保持完整。`records_kind_occurred_at_idx(kind,occurred_at,id)`及`records_occurred_at_idx(occurred_at,id)`分别支持类型联合日期、单独日期筛选。写入、读取、核验及导入检查列与原文一致，hash不能单独抵扣投影漂移。

- `occurred_at`是用户原话/事件发生日期，不是入库时间。接受严格`YYYY-MM-DD`或带`Z/±HH:MM`时区的ISO时间（秒必填、可选1–6位小数）；无日期用`unknown`、`未知`或`历史未知`，SQL投影为NULL、payload保留原值。不猜历史日期，不静默修正非法日期/时区。
- `search`增加`--kind user|debug`、`--from-date YYYY-MM-DD`、`--to-date YYYY-MM-DD`，可单独或与关键词组合；只按类型/日期检索时可不写关键词，但不允许完全无条件扫描。
- 日期区间包含首尾日，依据**原来源所写的日历日期**，不是把不同时区转换成UTC瞬间比较。未知日期不进入日期区间结果，仍可由关键词、类型或ID查回。日期非法/区间倒置拒绝；输出保持按ID稳定排序和原有分页上限，不宣称按时间先后排列。
- 新库及交换包使用schema 2。已有schema 1库不会自动原地改写：保持旧库原件，用之前匹配的工具导出，明确采用时在独立新责任区副本初始化同scope/README/描述/可见性与额度的新库，再显式导入schema 1交换包。核完整记录、旧摘要修订、hash及新列后再切换README入口；不覆盖旧库、不改真实工程。schema 1/2交换包均校验后整批导入；旧文本日期不合新格式时整批拒绝，保留原包，另核来源处理，不能自动改原话迎合校验。schema 1工具不能读取新库/包。

## 有限摘要与压缩授权

默认值为 USER **4000**、MEMORY **6000**、DEBUG **6000 Unicode字符**，包含头部、空白、索引和变更记录；不是token，不是用户指定数值。可通过区域工具显式调整，必须有限且在README/摘要头可查；禁止为了这次写入自动抬高额度。达到80%提示整理；超过上限拒绝工具写入、不截尾、不默默丢条目。

本规范被项目明确采用后，获授权维护该区域的Agent可对三份摘要不定期整理/压缩，不再仅限专门审计模型；只读任务不写。权限只覆盖三份摘要及其同scope历史，不扩到README、人类设计书、其他区域、源码或宿主记忆。未采用者沿原保护规则。

流程遵守“先归档、再压缩”，不将旧摘要存在等同于精选原话已入库：
1. 读取现状、责任区和实际额度，核人工改动与唯一写者；新来源先选录并完整读回，不能到压缩时才发现原话丢了。原话不可取回就标摘要来源，不能编造引文。
2. 先将将要淡出摘要的用户原话/已验证debug完整入库并验证，语义核对条件、例外、有效约束和证据未丢。一般模块知识不是user/debug时不伪装成这两种记录；它仍可保留在MEMORY当前摘要，或原有深度设计中。
3. 拟写有限的新摘要：保留当前关键事实、不可破坏约束、真实scope/README、DB入口与少量有用记录ID。旧详细变更记录也要收敛，不再把每次历史追加入Markdown。
4. `replace`带原文SHA和关联记录ID，工具先保全**三份摘要中本次被替换文件的完整旧修订**并读回，再写候选。USER/DEBUG须列真实精选记录ID；MEMORY仅含一般模块知识时可空ID列表，由旧修订提供恢复依据，不伪造user/debug记录。旧修订是压缩恢复证据，不是新精选事实，也不把快照中的猜测变成已验证结论。这层恢复资料只在压缩发生时保存，不周期性备份全项目、不复制会话。
5. 写后核字符数、原文可读、记录ID和有效意图未变。缺库、损坏、超额、记录缺失、旧文hash漂移或锁冲突就停止本项，保持原文并说明未完成；不能声称“已压缩”后让用户自己找回丢失内容。

语义筛选/压缩由Agent或人完成，本工具不调用模型、不自动抓取会话、不设cron、不安装Git hook，也不能阻止别的编辑器直接超额写文件。每次交付读取`status`并确认三份存在且不超额；使用工具`replace`才有硬拒写。审查不得将普通写文件绕过工具视为合规。

## 工具入口与真实边界

Python 3.10+标准库工具：`scripts/memory_history.py`。每个命令必须显式指定实际 `--area <路径/Agentic>`。初始化须显式给真实README相对路径、scope、说明和public/private；查询不创建缺失数据库。完整命令和可调参数集中在[README](../../../README.md#区域历史与有限记忆)。

- `init`建立库；`add`写精选JSON，`get <ID>`完整读回。
- `search [词]`按解码后的实际字段值做字面子串检索（含中文、双引号、反斜杠和换行），不搜索JSON键名/转义文本；可组合上述类型和日期筛选，命中后按ID稳定分页，返回有界索引、`has_more`和`next_offset`。查询先在同一只读事务流式核全部记录的hash及日期/类型投影，损坏报错而非伪报零命中；因此校验开销随精选记录数增长，不是向量搜索或FTS5，不承诺无限数据量性能。`get`才取全文。
- `status`显示额度、每份实际字符/旧文SHA、缺失、80%提示及超额；`limits`显式改区域额度，不改全局设置。额度已提交但摘要回读失败时返回`committed=true`、实际`limits`与`status_error`，先修文件再读status，不把此结果误判为写入失败而重放。
- `replace`安全替换候选；`snapshot <ID>`完整读压缩前旧修订。恢复须先保全现状，再另行核定恢复内容，不能盲重放旧任务。
- `verify`核库与载荷；快照读取、verify、导入和导出复用同一套字段类型、主键/hash、旧文hash、有效来源ID列表与引用可达性检查。`export`/`import`交换确定性JSON并严格校验scope、hash与ID冲突。最终校验在导入提交前完成，失败整批事务回滚、不覆盖现有摘要；导出在一致读事务校验并读取，不覆盖已有输出文件。

SQLite事务不与文件系统构成跨介质事务。工具先提交并读回归档、同目录临时文件写入和原子替换，失败可留下“已归档、未替换”的旧文证据；不能把快照存在当替换成功。锁仅串行化本工具写者，摘要替换前后核hash不等于能阻止未配合锁的外部编辑器在极小时间窗内改写。必须保证唯一写者；锁残留先查原任务/进程，不自动删锁抢写。DB与摘要不得使用符号链接；脚本不承诺对恶意本机并发文件替换提供沙箱隔离。

## 共享、隐私和迁移

- SQLite内容不会因二进制文件就自动私密。数据库、journal/wal/shm、导出和候选摘要都须明确访问与发布边界；默认不公开入Git。真实工程采用时在授权范围加入精确忽略规则，已跟踪文件仍需另查；工具不会自行改Git配置。
- 不在活动写入时裸拷贝数据库，不用Git文本合并SQLite二进制。跨机共享采用经来源/隐私核验的JSON导出导入，受信任单writer可另用SQLite正规备份；JSON是交换制品，不做另一套长期注入文档。共享摘要的历史ID必须随获准共享的完整记录可达，不能只提交MD留下别人无法打开的私人DB。公共工程导出前再次逐条脱敏，不能靠`redacted`布尔值当自动扫描。
- 不把宿主私有USER/MEMORY、私聊、凭据、企业秘密、他人profile历史搬入项目库。已脱敏原文须清楚注明，不能声称保留了未提供的秘密原件；敏感原件留原合法来源。
- 采用范围内的旧USER/DEBUG先逐条核来源、补齐scope、选录和读验，再压缩；仅旧摘要可获得时保留为旧修订并标来源缺口，不伪造用户原话。MEMORY一般知识只做可恢复摘要整理，不冒装成用户或debug历史。
- 库/导出属于有价值的项目历史，不能因“仅保留三份滚动备份”清掉唯一记录。增量去重靠稳定ID和修订关系；不按时间自动清理原文。安装本技能、提交本PR不代表业务工程已经迁移、其他Agent已经加载或自动注入机制已经接入。
