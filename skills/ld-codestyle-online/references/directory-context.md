# 目录级共享上下文：README 与 Agentic 记忆

本组文档面向**不同厂商、不同会话的 Agent**，也便于人类查看。它们是项目内、当前区域的共有参考，不是绝对结论，也不是Hermes或其他宿主的全局人格/私有记忆导出。此规范不会让不支持这些文件的宿主自动加载；采用技能的Agent须主动读取。

机制的作用是让接手者找到**本区域的需求、经验和真实使用/测试方法**，减少重复解释与跨模块知识污染。README 负责发现和声明范围，其余共享记忆集中存放；文件名和存放位置都不扩大权限。

采用本版规范后，适用区域内原来放在其他位置的**既有共享记忆也必须迁移**进该区域的 `Agentic/`，**不是仅新建文件**采用新路径，也不是可选布局。迁移仅存放位置改变，内容归属、逻辑作用域和原有约束不降级；README原有职责与权威索引保持不变，不移动README、不把它改成只剩跳转链接的空壳。适用范围内有真实冲突时按下述规则记录“迁移未完成”及责任人，不将旧位置永久保留为合规例外。

**安装/更新技能不触发全机或全仓扫描**，也不改变正在执行任务的规则版本。在已采用规范且本轮获授权写维护触及的责任区域，主动完成可安全保全的旧记忆迁移，无须另等一次迁移许可或逐文件重新请示；只读任务不搬迁。明确采用/升级项目规范或迁移任务完成已确认范围，不因局部小修扩大为全仓搬迁。较大范围可分批保全迁移，列明已完成区域、剩余范围及下一责任，不把分批当永久例外，也不把未完成部分说成合规；真实冲突仅暂停冲突项并记迁移未完成。

## 位置与作用域

以实际 Base 类型及配对接口所在的位置为控制区域，通常也是人类观察、调整底层的入口。目录可能叫 `Scripts`、模块名或其他名字，**不要求新建字面名为Base的目录**。区域根可记为 R。

**物理存放与逻辑作用域分开**：`R/README.md` 留在区域根，声明 `Agentic/MEMORY.md`、`Agentic/USER.md`、`Agentic/DEBUG.md` 的存在、职责和负责路径。除 README 外的同类共享记忆正文集中在 R 的 `Agentic/` 中；它们的逻辑作用域是 **README 所在区域 R 及其子目录的脚本与资产**，等同于直接放在 README 同级的区域上下文，**不是只管 Agentic 实现目录**。这里的“同级权威”指相同责任范围，不表示高于用户指令、工程规则或真实代码。

```text
<Module>/Scripts/                 R：本区域根
  FeatureManagerBase.cs
  IFeatureManagerBase.cs
  README.md                       声明R、边界与下列记忆入口
  Agentic/
    MEMORY.md                     逻辑scope=R，不是R/Agentic
    USER.md                       逻辑scope=R
    DEBUG.md                      逻辑scope=R
    <可替换实现>
  <相关子目录与资产>
```

每份文件写明逻辑作用域、所属 README 的实际相对路径及必要排除项。Agent 先读 README 的声明，不能仅按记忆文件的物理父目录推断范围，也不能因为位于 Agentic 就限制它无法记录相邻 Base/接口。相反，`R/Agentic/OtherModule/README.md` 声明的独立子模块只管其明确区域，不借“向上一级”规则取得整个 R 的范围；**向上锚定必须来自所属 README 的明确声明，不自动对所有 Agentic 层层上提**。

### 区域隔离与跨区域索引

- **不得把兄弟目录**、其他项目、无关任务或宿主私人记忆的内容混进本区域正文。文件应随知识的实际责任归属维护，不能为了方便搜索把所有内容灌入一个模块。
- 父级保存真正跨本区域成立的共性、边界与子模块地图；子模块保存自己的具体需求、经验与流程，不在父级堆其内部实现细节。多个 Base 共用同一控制区时共用一组，不给每个类建立一组。
- **跨区域索引**可以包含已核路径、关系类型和必要的一句说明，例如“本模块调用 B 的加载入口，契约与测试见 B/README”；这是关联入口，不是把 B 的知识复制成 A 的有效规则。读取索引目标时先核其 scope，信息可作依赖参考，但不会因被链接就继承对方权限或改写本区域约束。
- 示例：`Core/Audio/Agentic/USER.md` 由 `Core/Audio/README.md` 声明，管 Audio 及其子路径，不管 `Core/UI/`。Audio 的 DEBUG 可记录“通过 UI 播放按钮触发 Audio”的本模块端到端验证，并链接 UI 的操作细节，不复制 UI 的全部需求。项目根 README 只索引两者及真正全局约定。
- 更近的文档可以细化上层规定，不能静默废除上层明确边界；当前用户要求按其真实任务、区域和时效范围执行，不把“本次只验某入口”存成以后只能验证该入口的永久规则。
- 只在有独立责任和真实增量时补子模块文档；不全仓机械铺空模板，不进入第三方/生成/缓存目录。

## 每份文件头部：独立可读的基础说明

**不能只在 README 写一次。**README、MEMORY、USER、DEBUG及同类共享记忆的**每份文件头部**，都必须在知识/业务正文之前保留简短、自足的用途与读写说明。临时接手者、其他人类队友的AI、未安装本技能或不在舰队/指挥系统中的陌生Agent，可能通过搜索直接打开其中一份；不能假定它已经读过README、技能或团队记忆。

独立打开任一文件，应能从头部知道：

1. **是什么**：该文件自己的具体职责；它是供人类和不同Agent接续使用的持久项目共享上下文，不是临时文件、缓存、任意日志或宿主私有记忆。README做区域地图与索引，MEMORY记事实/经验，USER记用户意图/要求，DEBUG记用户操作/测试流程，不能只写笼统的“记忆文件”。
2. **管哪里、从哪里继续读**：具体逻辑作用域、必要排除项、所属README的真实相对入口。README声明自身区域与记忆入口；Agentic内的记忆说明其scope与所属README同级，不只管Agentic、不扩及兄弟区域。模板占位须落成真实路径；缺失或未知明确写出，不编造链接。
3. **怎样使用和更新**：改本区域前先读适用条目并核来源、实际代码/版本；仅在当前任务授权内更新有来源的真实增量，保留有效正文、条件和用户原意，记录日期、变更原因与实际模型身份。不得擅自删除或改作他用，也不能把持久属性误解成永远不可维护。
4. **整理与权威边界**：普通Agent仅在九成以上把握时去除明显重复或无损整合，否则不动；内容压缩限专门获授权的审计/辅助模型。内容是可回核参考，不高于当前用户指令或系统安全边界；旧要求、设想、推断与DEBUG步骤不自动生成新授权，未知先标待核，不把未经验证的结论写成事实。

这段基础提示不是System Prompt、不是另一套指挥系统，也不保证宿主自动加载。用通用语言解释职责和边界，**不能只写“遵循CodeStyle/舰队规则”、只给技能链接或只让读者回README**。细则可以链接，但链接不能代替本文件里的最低说明。每个头部只保留最小必要信息，不复制完整技能、其他文件正文或内部舰队资料。

**旧文件同样适用**：在已授权采用/升级或维护该区域时，为缺说明的既有共享文件补齐头部，不是只有新建模板有说明。按原scope保留有效正文、来源、历史记录与Unity `.meta`；只补说明不重写全文件、不清空旧知识。普通已授权写任务只处理触及范围，明确采用/迁移任务按其范围处理；只读任务只报告缺口，历史人类Readme及所有权冲突继续走原保护规则。本技能源仓的提案不等于已给业务工程旧文件补齐。

## 文件各记什么

### MEMORY.md：区域事实、经验与解释

保存对后续处理有用的模块知识：框架逻辑、数据流/生命周期、业务意图、已踩的坑、bug及根因、可复用修复经验、资源/序列化/依赖约束、验证入口。说明适用文件/条件和可核依据。

已验证事实与待验证推断分开；一次实测只证明当时、该版本和该条件下的结果，不直接构成长期可靠知识。不要把某Agent一次猜测写成模块真相。缺陷修复经验在修复并验证后，记录“发现与复现→历史修复核对→有效修复过程→验证与防复发边界”，而非全量排错流水；尚不确定的根因只能作为该已验证结果的限定解释，不能借“暂定参考”收进未完成的修复计划。结论措辞按下述成熟度调整。不写私人称呼、人格、私密对话、账号或机器秘密，不复制宿主的MEMORY.md。

### 复发缺陷的修复经验闭环

**工作会话中发现或用户反馈的 bug 反复出现，尤其 Git 日志显示曾经修过时，必须在已验证修复后，主动记录或更新所属区域 `Agentic/MEMORY.md` 的修复经验。**不能只在聊天回复、提交说明或临时工单里说“又修好了”。没有找到历史提交不免除有效经验的沉淀，也不能据此编造“以前已修复”。范围仍以所属README声明为准，不搬Bot私有会话，不全仓搜集无关故障。

1. **先核历史再修**：从现有MEMORY、相关Issue/PR和目标路径的Git历史查关联提交，读实际 diff、适用版本及当时验证；提交标题写“修复”不是生效或根因相同的证明。区分修复未进入当前分支/未部署、后来回退或覆盖、原修复漏了条件，以及仅表象相似的新原因；未查明就保留待核，不为填记录强行归因。
2. **记录时机是有效修复闭环之后**：本轮修复已落地，并在明确范围真实验证通过时，再回述发现、定位、有效修复步骤和结果。不必等待整项任务、合并或发布才写；未推送/未合并/未部署的层级如实标记，不将局部验证写成线上已修复。仅发现问题、写了补丁或编译通过，而对应缺陷尚未验证，不算该缺陷已解决。
3. **同类知识更新同一条目**：就近保留简短标识、发现/复现条件与用户可见影响；相关历史修复提交/Issue和本次关系；已证实原因与仍待核解释；本次有效修复过程及关键改动入口；被测版本/环境/日期、复现前后结果和真实证据；防复发条件、相关DEBUG流程及适用/未覆盖范围。未知就标未知，历史提交或验证不存在时不补造。正文保留能复用的因果与必要步骤，详细日志链接原任务，不能只写“已修复”或堆所有命令。
4. **不收半途噪音**：修复中途的尝试清单、未验证猜测、准备做什么，以及废弃/放弃但未形成有效结论的方案，不作为新增修复经验写进MEMORY；放原任务/Issue保留必要取证即可。修复闭环后可保留直接解释有效方案的已证实避坑结论，不复刻无价值试错流水。减少噪音不等于清理历史：不删除任务证据、有效旧经验或有价值反例，也不获得内容压缩权限。
5. **阶段性/番茄切片成功修复是有效成果**：切片内有明确缺陷、已落地修复和真实验证，就可记录该切片，不视为半成品噪音；写清“本切片已修复什么、适用条件、尚未完成什么”。大任务未结束不影响入库，但不把大任务的完成状态一并升级，也不因到了切片时间、只做了调查或测试尚未通过而宣称成功。
6. **复发后纠正旧经验，不维持虚假可靠性**：出现可核反例时，可立即给既有条目标记“已复发/待复核”、缩小适用范围并链接原任务；这是纠错，不是提前发布新的修复经验。新修复验证后再更新有效结论、前后适用条件和替代关系，保留日期、实际操作模型与原证据。已验证修复不等于长期稳定；按下述成熟度规则继续复核，不重新等待7/15天才允许记录这次真实结果。

MEMORY保存“为何发生、如何有效修复、怎样避免重犯”的经验，DEBUG维护“从用户入口怎样操作和验证”的流程；二者以条目标识/相对入口关联，不复制两份日志。原任务/Issue保存调查过程、未完成项和下一责任人，不能用写MEMORY替代实际修复。

以下为入库判断示例，不是项目事实：

| 情况 | 处理 |
|---|---|
| 用户再次报告同类问题，Git有旧修复，本次修复已实测通过 | 更新同一MEMORY条目，串起旧修复、复发条件、本次有效过程与回归证据。 |
| 找到旧“fix”提交，刚写新补丁，尚未跑相关失败场景 | 不新增“修复成功”经验；调查与补丁进度留任务/Issue。 |
| 番茄切片修好一个入口且已验证，另一入口仍未完成 | 可记录已成功切片，明确未覆盖入口与剩余项，不等整个任务收工。 |
| 已放弃方案，只有猜测和零散尝试 | 不灌入MEMORY；保留原任务中的必要证据。 |
| 已有经验声称有效，但新的实测提供反例，本轮尚未修好 | 立即给旧条目标待复核并链接证据；新的修复经验等验证后再写。 |

### USER.md：用户意图、持久要求与业务演进

保存用户针对本区域提出、仍有持续价值的注意事项和关键约束；当前业务需求允许动态更新，另记用户视角的历史痛点，以及未来铺垫与设想。

- 区分**已明确要求**、**当前业务需求**、**未来设想/待探索**、**Agent待确认解读**。后两类不当成当前实施授权或用户已拍板。
- 保留必要的脱敏出处/日期和生效条件，摘要标明是摘要；不伪造“用户原话”。用户视角描述可由Agent归纳，但不能以自己的偏好冒充用户要求。
- `USER.md` 同样是参考：尽可能保留整理后的用户原话意图、关键用词、否定和例外。原话摘录与意图摘要分开，摘要注明“当前理解/待核”，必要时并列保留可脱敏引用的原句。不得为了加“可能”而改写引号中的原话，或把明确要求弱化成可选项。
- 不收“这次换一个字/临时调一个值”等一次性工单，不把一次修复无限外推为永久规则。
- 新需求替代旧需求时更新当前有效结论并标明替代关系；旧内容可标失效并指向可恢复原文，不把失效项继续当当前指令。更新不自动授权压缩历史，未明确撤销且仍适用的约束不能仅因旧就删除。

### README.md：区域地图与快速入口

给出该区域的业务描述、责任/非责任、主要路径及子目录用途、Base/接口/活跃实现入口、常用操作和验证入口；把常用或复杂的关键信息指向具体文档/位置。

**README原有职责与权威索引保持不变**：继续承载原有业务说明、区域边界、操作入口与权威指路，记忆索引是补充职责，不是替代原内容。迁移MEMORY/USER等时不将README搬入Agentic，也不把原有有效说明挖空。

README **头部、业务正文之前**必须有简短且自足的机制说明，让**未安装本技能**的 Agent 只读该区域README也能知道：
- 本区域使用项目共享记忆机制；`Agentic/MEMORY.md`、`Agentic/USER.md`、`Agentic/DEBUG.md` 等的具体职责及真实相对入口。
- 它们虽然物理存于Agentic，逻辑上仍是README同级区域上下文，覆盖此区域及子路径；不是仅供Agentic代码使用，也不扩展到其他区域。
- 这些是持久的项目共有知识，**不是临时文件、缓存或Bot私有记忆，不得擅自删除或改作他用**。修改相关区域前应读适用条目，改动仍受当前任务、来源与文件内约束限制；不能因没安装技能或目录名叫Agentic就忽略这些职责。
- README及记忆中的关系索引只指路，不把其他区域正文复制过来，也不授予额外权限。

这段说明不能只写“遵循某技能”或只给技能下载链接；关键含义应在本文件内即可读懂。详细规则可链接，但不要求陌生Agent先安装技能才能理解存储与作用域。模板中的占位入口须在落地时换成真实相对链接，未建立的文件明确标记缺失，不能宣称已经存在。

### DEBUG.md：用户操作与正确测试流程

`Agentic/DEBUG.md` 保存本区域模块/功能**从用户视角如何实际使用和验证**，不是只列开发者命令、编译步骤或 bug 日志。开工先找相关流程；会话和开发过程中，用户说明正确顺序、纠正错误操作、补充成功/失败现象时，及时提取为**流程修订**，保留用户原意、适用范围、来源日期和关键条件。用户纠正与 Agent 提议分开，未确认的步骤不冒称用户指定；准确摘录不擅改，过期流程标明替代关系。

每条流程用简短标识，按需要记录：
- 用户目标、具体模块/入口、适用功能和不适用范围；该流程来源于用户描述、已验行为还是 Agent 待核提案。
- 前提：版本/平台/场景、所需配置/权限、准备状态、隔离测试数据与必要依赖。凭据只指合法获取方式，不写值。
- 操作步骤：从真实入口依序打开、选择、输入、触发；每步写预期可观察反馈。正常路径之外，补与本次改动相关的取消、错误或恢复路径，不机械扩成全产品审计。
- 预期与实际分列：成功标准可由画面、声音、交互或数据结果观察；流程尚未运行就写“未验”，不能预填通过。
- 清理/恢复：只撤本次测试对象、恢复约定状态，保护真实用户数据、成绩、未保存编辑和其他任务。
- 最近实际执行的日期、被测版本/提交/制品、环境、流程修订号、结果/证据和未覆盖项；详细日志只链接，不塞满长期流程。

### 推送后与合并后的回归

1. 推送前按改动影响选出相关 DEBUG 流程并实际运行可用部分；没有流程时，先从用户已说明的操作与真实入口建立有来源的最小流程，不拿想象填通过。
2. **推送后**先核远端准确提交，再针对被推送版本尝试相关业务流程。**PR/分支合并后**核合并结果提交/制品，对整合后的版本再尝试；分支上通过不能冒充合并版本通过。未发生合并就明确“未合并，合并后回归尚未执行”，不为了满足测试要求自行合并。
3. 确认测试环境实际加载目标版本。未部署或未加载时只记已验证层和待验证版本；若需构建/部署而当前未获授权，说明阻断、下一动作及责任，不把旧运行版本的结果套到新提交。无关文档变更可说明哪些业务不受影响、只验声明/索引与相关工具入口；不全仓重复测试。
4. 有条件的相关流程应真正执行，不能只阅读 DEBUG 后打勾。缺设备/权限/数据、危险动作或人工审美项未完成时，明确记“受阻/未验/需人工判断”，不能编造成功；**不自动授权**外发、付费、删除生产数据、重启共享服务、覆盖人工内容或部署新版本。
5. 失败先保留现象、步骤、版本和证据，判断产品缺陷还是流程失效；**不能为了测试通过**改低预期、略过失败步骤或清掉错误。只有真实用户纠正、产品设计变更或可核验证据支持时才修订流程，保留理由与旧版本指路。
6. 新的实质改动使旧证据不再覆盖时，重跑受影响流程。纯验证记录补写不制造无限“写结果→推送→再写结果”循环：结果可留原任务/PR并链接，精确标明被测提交与记录提交，不把记录日期当执行日期。

## 参考措辞与知识成熟度

`MEMORY.md`、`README.md`、`USER.md`、`DEBUG.md` 及同类共享记忆均提供可回核的上下文，不能凭文件名、记录时间或推送次数成为绝对事实或新的授权。以下阶段针对**每项结论及其适用范围**，不整份文档一起升级。DEBUG的一次实际结果准确记录；从该次结果推导的长期可靠性才另看成熟度。

### 首次记录

- 新增的解释、根因、经验、设计效果和用户意图摘要默认是**暂定参考**。按证据自然采用“可能”“预计”“估计”“当前理解”“在本轮条件下”等措辞，并写清依据和未核部分；不机械给每句都加同一词。
- 可复核的观察应准确陈述：例如“本轮三次保存测试通过”，同时注明版本、日期和条件；推论另写“预计可缓解该条件下的丢失，其他入口待核”。不要把已发生的观察写成“可能通过”，也不要从它推出“以后绝不会丢失”。真实路径、命令和原话同理。
- 记录首次日期、最近核验日期和来源；尚未推送就明确未推送。存在较早、可核的相关推送及验证证据时可以引用，不要求为了新建文档重演历史；没有证据不能凭旧文件时间补出成熟度。

### 从暂定到基本稳定

时间以**首次含该结论所依赖实现或记录的、可核实的远端推送**为起点；本地提交日期不是推送日期。Git 本身不存推送时间，优先引用可核的远端事件、PR、发布或既有推送记录；只能证实某日已在远端时，以该日作保守起点，证据不足则保持暂定。不要为了成熟度主动提交或推送。

| 阶段 | 必要证据与处理 |
|---|---|
| 暂定参考 | 首次新增、未推送、证据不足，或未满足后续条件；保留不确定性和待核范围。 |
| 持续观察 | 首次相关推送后**超过 7 天**，再次涉及该条目并复核仍一致；可补充“截至某日，在这些条件下仍符合预期”，尚不能固化为基本稳定。 |
| 基本稳定 | 首次相关推送后**超过 15 天（半个月）**，已经历**多次相关推送**及不同时间的重复核验，证据一致且无未解决反例；在再次涉及该条目时才考虑修正措辞，注明稳定范围和依据。作为保守执行口径，多次取至少 3 次独立相关推送（含首次），不把同批多个 commit 当多次推送；项目/用户有明确口径时遵循并记录。 |

上述是候选门槛，**时间和次数本身不是正确性证明，不自动升级**。无关推送、为凑次数拆推、同一结果的复制、无人报告问题，都不能代替相关验证。没有在一周时处理过的条目，超过半个月后可以在再次涉及时一次复核全部条件，不需要后台定时器或强制周报。

- “基本稳定”表示在注明的版本、场景和前提下可较可靠地复用，仍是可修正参考；不写成永远正确、全场景适用或免测试。到期也不自动改文档、安装技能或扩大执行权限。
- 反例、用户纠正、依赖/架构/业务条件变化出现时立即标记待复核或降级，保留可恢复的历史及替代关系。结论实质变化时为新版本重新记录证据和观察起点；未变的独立结论不陪同归零。措辞润色不重置原有有效证据。
- `USER.md` 的成熟度评估针对 **Agent 的归纳是否准确、是否仍适用**，不是评判用户意图真假。当前明确用户指令立即按其适用范围执行，不等 7/15 天，也不因摘要“基本稳定”而覆盖新指令；旧摘要不能成为新增授权。
- 就近用简短行或小表保存状态、首次记录/相关推送、最近复核、关键证据和边界。README 可以链接同区域 MEMORY 中的成熟度记录，不复制一份时间账；不为每个路径、标题或机械事实建立重型台账。

### 措辞与复核示例（仅为示例，不是项目事实）

- 新增 MEMORY：“修复并验证后记录，长期解释暂定；本轮提前捕获保存快照，原入口复现用例不再丢失；根因可能与快照捕获时序有关。依据：实际版本与回归记录；并发场景未验，不据此宣称全局可靠。”
- 新增 README：“当前实现预计由 `FeatureManager` 承担此入口；已核的文件和验证范围见同组 MEMORY。”路径须先确认，不能照抄示例当真实类名。
- USER 原话摘录：“尽量不影响插件源码（除非必要）”；意图摘要：“当前理解：优先项目侧扩展，必要改插件时说明依据；并非绝对禁止改插件。”
- 满 7 天但未超过、仅两次相关推送、超过 15 天却没有复核、或仍有反例：均不能标“基本稳定”。超过 15 天且至少 3 次相关推送及重复验证仍一致：再次涉及时可按证据提升，仍标适用范围；旧日期未知则不推算为已达标。

## 日期、修改身份与简短变更记录

- 所有记忆类文件（包括承担共享记忆职责的 README、MEMORY、USER、DEBUG、Agentic 索引及同类文件）尽可能标明创建日期、最近修改日期；新建/本次实际修改使用真实日期，跨时区有歧义时注明时区。**历史日期未知**就明确未知，不以文件mtime或当前时间补造原始日期；不为补日期全仓触碰历史人类文件。
- **文件更新时间不等于验证日期**，也不等于首次可核远端推送日期、用户要求提出日期或生效日期。每种日期按其含义记录；润色/搬迁不能让旧证据看起来刚测过。
- 对条目**新增、修改、删除**（含替代、迁移、去重或获准压缩），在该文件就近留简短变更记录：日期、条目标识/受影响小节、动作、原因/来源或替代指路、实际操作者身份。可将同一批有关条目合成一条，但必须能看出改了哪些，不用每句附长签名。
- 身份沿用[Commit身份要求](commit.md#客户端bot-与计算机身份)：`##模型：<真实Bot/客户端名> + <实际模型标识> | <本次记忆变更摘要>`；本地/默认 Agent 按该规范带真实计算机名，已核独特 Bot 的例外保持。不能只写“AI/Codex”、猜模型，或把整理者当原需求作者；用户原话仍保留其来源。
- 删除正文后仍留下**删除摘要**或替代指路，记录删的是哪个条目、为何删、由谁操作；不把应删除的敏感原文重新抄进摘要，不靠Git作者或“最后维护者”一行替代条目变更来源。整文件迁移/删除时在所属README或接收文件中留同范围索引与简短记录。
- 改动记录不是权限：既有人工保护、九成以上把握的无损整理与专门压缩授权仍适用。只保留有用摘要，旧详细记录指向可追溯任务/提交；不擅自压缩、删减或伪造他人的维护历史。

简短示意（占位值须换成真实值，不是已发生记录）：

```text
日期：<YYYY-MM-DD / 时区>；动作：修改；条目：<流程或知识标识>；原因：<来源/修正>。
##模型：<真实Bot名> + <实际模型标识> | 修正指定条目的操作顺序
```

## 历史 Readme 与跨平台冲突

**历史 `Readme.md` 一般是人类资料，默认不覆盖、不改名、不自动改写，不因本规范接管。**其他已有、未明确归为Agent共享入口的 `README.md`/`readme.md` 也先保留。

Windows以及常见macOS卷不区分大小写，因此 `README.md` 与 `Readme.md` 在同目录不能可靠共存。即使当前Linux允许，也不得制造只在大小写上不同的两个Git路径，交给其他平台时会冲突。

新建前用文件工具核实际目录名，并用 `terminal` 的Git索引检查已跟踪路径（例如 `git ls-files -- <目标目录>`）；不能只看 `README.md` 是否存在。按以下顺序处理：

1. 在已采用规范且本轮获授权写维护触及的责任区域，主动盘点旧位置的共享记忆并按原责任区域迁入其 `Agentic/`，安全保全搬迁无须逐文件重请；明确采用/升级项目规范或迁移任务则完成其已确认范围。**既有共享记忆也必须迁移，不是仅新建文件**这样放。不再新建同层 MEMORY/USER 或 AgentDocs 记忆组，不以“旧文件先留着”为完成。区域根README的位置、原内容职责与索引权威保留，并在头部补机制说明及准确入口；只读任务不搬迁，安装/更新技能不触发全机或全仓扫描。
2. 无冲突时在区域根保留/创建共享 README，声明 `Agentic/` 的记忆入口。若历史人类 Readme 的拥有者明确同意，可只补必要声明/索引，不重写原内容，也不另建大小写变体；未获允许不能直接接管它。
3. **旧 `AgentDocs/` 是兼容过渡入口，不是新版默认存储区。**在采用本版规范的区域，将非 README 的共享记忆正文保全移动到所声明区域根的 Agentic，更新所有受影响入口及相对链接；原 AgentDocs/README 或旧记忆路径可仅留迁移索引，声明唯一新正文。根 README 无法安全补声明时，保护旧资料并明确“迁移未完成”、具体冲突和下一责任人；解除冲突后继续完成，不将旧布局认定为永久例外，也不另造第三套目录。
4. 迁移先核目标无同名覆盖、无人工脏改动，确认根 README 的声明范围与每份旧文档原scope一致；文档及其 Unity `.meta` 一并保全，验证内容/来源/条目标识/链接，再停用旧正文。采用/升级范围内的迁移属于规范落实，不把普通文件搬迁变成逐文件重新请示；范围外工程、宿主私有记忆和未获许可的人工内容仍不动，重叠条目不因移动而自动压缩或丢弃。
5. 仅允许**单一有效正文**。旧路径作为索引时只能含新路径、原scope和必要迁移说明，不保留另一份待更新正文；未知冲突保持原位并标待处理，不以复制双份假装迁移。

兼容迁移示意（适用区域落实新版规范，保护原内容与索引职责）：

```text
<Module>/Scripts/                 R
  README.md                       或获准补声明的既有Readme.md；不并存大小写变体
  Agentic/
    USER.md                       原内容/来源保留，scope=R
    MEMORY.md                     scope=R
    DEBUG.md                      scope=R
  AgentDocs/
    README.md                     若需保留旧入口，只索引新的声明/正文
```

Agent 查找时先读区域根的实际 README/Readme，再核已存在的旧入口和声明；迁移旧根目录 MEMORY/USER 是保全搬迁，不是当垃圾删除。某文件有独立明确职责而非共享记忆正文（如宿主 `AGENTS.md`、Core `Agentic.md` 索引）时保留其既有位置，不机械搬进 Agentic。仅安装技能或修改本技能源仓PR不等于已经迁移业务项目；只读任务发现旧布局时标明待迁移，不谎称已完成，也不越出本次项目/区域授权。

## 读取、更新和权限

1. 开工沿已采用规范的模块层级，从上层到目标区域读取文档组；先读 README 的区域声明，再读其指向的 Agentic/USER、MEMORY 和相关 DEBUG 获取意图、经验和使用/测试流程。同时检查相关脚本附近的旧 MEMORY/USER/DEBUG、AgentDocs 等入口，不能只找新布局而漏掉尚未迁移的要求。旧布局按既有明确scope解读，不能仅按物理父目录缩小或上提范围。结合最近工程指令、真实Base/接口与活跃实现，不得向工程边界外扫宿主私有文件。
2. 上下级文档冲突先核原请求、适用范围与来源。更近的文档可以细化而非默默废除上层强约束；当前明确用户指令优先。文档只是可核上下文，不因文件名而获得高于系统安全或当前授权的权限。
3. 在已授权的写任务触及该区域时，补缺的文档应有真实内容，有增量就就近更新；只读查询不创建、不修改。原任务本应继续时不能用“已补文档”替代代码/资产交付。
4. 基于本轮实测、用户纠正或结构变化更新对应区域的有效结论和DEBUG流程；保留日期、实际模型身份、简短条目变更与成熟度证据，不每次机械追加聊天。首次新增不直接固化；再次涉及才复核是否满足升级条件。长期约束留本组，原始事务/详细日志留原任务；已有内容的去重、整合与压缩须分别遵守下述权限，不能借“持续更新”删减未重复的信息。
5. 不跨厂商复制私人记忆。共同知识允许不同Agent维护，但重要要求来源不明时标待核，不编造授权；修改安全、契约或大范围设计仍走原权限流程。
6. 放入Unity Assets时按正常Editor导入产生 `.meta`，保留已有GUID；文档规范不授权手改场景/预制件或任意重导入。需要提交时检查真实Git状态与忽略规则，不能因文件名常用于私人记忆就静默漏提交，也不能强制把所有记忆文件纳入仓库。

## 去重、整合与内容压缩的权限

- **普通Agent**可以剔除明显重复内容或进行无损整合，但须判断对此操作有**九成以上把握**。达不到、不能确定信息等价或有歧义时，直接忽略这项整理，保持原文，不影响其他已授权工作。
- **无损整合不等于压缩**：必须保留所有独立事实、适用条件、限制、来源、用户原意、确认/探索状态及仍有价值的差异。不能因为“看起来差不多”就合掉互有条件的要求，也不能借去重抹去矛盾或未知项。
- **内容压缩**（摘要化、抽象替代细节、缩短到可能丢失信息等）通常不由普通Agent处理；仅交由**专门获授权允许的审计/辅助模型**在授权范围内执行。自认为更强、更有把握、承担普通审查，均不能代替这项专门授权。
- 获授权压缩也须先保留可恢复原文，再检查事实、例外、来源及用户意图没有遗失或损坏；不能以节省token或文档太长作为越权理由。
- 本边界适用于 `MEMORY.md`、`USER.md`、`README.md`、`DEBUG.md` 及同类共享知识文档。“持续更新”授权不自动扩大为内容压缩授权。

## 与既有文档分工
