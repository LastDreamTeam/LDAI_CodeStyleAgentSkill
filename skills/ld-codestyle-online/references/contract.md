# 协作契约

本页为基于 LD v6 及人类已确认补充的公开整理。以当前请求、最近工程规则、真实代码与公共/序列化契约为准；不是一次性批量重构授权。

## 模块结构与控制边界

```text
<Module>/Scripts/
  I<Feature>ManagerBase.cs
  <Feature>ManagerBase.cs
  MEMORY.md                  共有经验与模块事实
  USER.md                    用户持久要求与业务意图
  README.md                  区域概览与快速索引
  Agentic/
    <Feature>Manager.cs
  Sample/ 或独立 Demo 入口（按需）
```

配对接口取 Base 类型的精确名称，包含 `Base` 后缀。接口仅放所有实现必需的契约，可以从小甚至空开始；不为未来猜测堆成员。使用无方法体声明，避免不必要的默认接口实现。Base 实现接口，可加必要 protected/virtual 扩展面和简单兜底。初建后配对接口变更须人类或明确授权的架构负责人裁决；普通接口按工程范围审查，不套一刀切审批。

Base 可迭代，不是人工审过的证明。应供派生调整的状态、属性后备、联动转换使用受控 protected setter/方法或 virtual；临时计算、内部缓存、不宜破坏的不变量保留 private。不得迫使派生用反射、复制状态、粘贴整段 Base 绕过契约。

Base/配对接口的属性至少有一份有效 XML 说明，优先放接口；同语义实现可 `<inheritdoc/>`。公共/受保护方法事件解释用途、约束与生命周期，不翻译语法。派生实现对外有用的成员也宜说明。

Agentic 目录权限继承父模块，不能跨越接口、序列化或兄弟模块边界。AI 非 Base 实现默认使用 `.Agentic` 命名空间，包含样例和 Editor 工具；复合业务、独立小脚本等有合理例外时说明，避免无意义包装。

## 目录与职责

- `Assets/Core`：可提取、业务轻的能力模块，附最简单的 Demo/使用入口。
- `Assets/Scripts`：跨模块入口、Model 和全局业务编排，不堆特定模块内脏活。
- `Assets/LastDream/Core` / `Assets/LastDream/Scripts`：混合工程中的隔离区或尚未提升到正式结构的实验能力，也是合法布局。
- 两套根依据现有所有权、成熟度和将来提取边界选择，不为美观互相搬迁。
- 模块内按需放 `Scripts`、`Resources`、变种和 Sample，不机械生成空目录。
- `MEMORY.md` / `USER.md` / `README.md` 在Base/配对接口控制区承载目录级共享上下文，细则见[目录记忆](directory-context.md)。历史 `Readme.md` 是原有人类文档，默认不干涉；存在大小写/所有权冲突时用 `AgentDocs/` 兼容布局，不覆盖它。
- `Agentic.md` 保留Core模块索引职责；与新README用链接分工，避免双份长期漂移，不自行删除或迁移旧文档。
- 美术源资料是长期资产，不擅自清理。Git/LFS 门槛按实际远端限制检查，不默认忽略整份美术库。
- 不因为插件“不整齐”就搬目录；核 GUID、asmdef、Resources、原生依赖后优先项目侧 wrapper/adapter，不改第三方原件。

## Model / Manager / ViewModel / View

默认调用关系：`Model/facade → Manager → ViewModel → View → Unity 可见对象`。

- Model 汇聚方便人类使用的业务动词和合理全局耦合；复用现行单例/facade，不为新功能重复造一套。
- Manager 管当前实现、创建/切换/显示/隐藏/释放与少量稳定 API；需要时可暴露具体 ViewModel，不强做无限转发。
- ViewModel 管不可见状态、规则、时序和输入解释；绑定和解绑匹配模块生命周期。
- View 管显示对象、UGUI、序列化引用、渲染和呈现事件，不反向承接业务决策。
- 单一机械行为/硬件/变换可用 Controller，不为一段小功能强造 MVVM。`View` 不泛指一切可见行为。
- Manager 挂父对象，名称体现业务及 `Manager`/`Mgr`；View/ViewModel 尽量同挂业务命名子对象，避免用脚本列表拼名字。
- Demo 是教学和最小验证场景，宜有独立同用途根对象，不默认塞成 Manager 的子业务，更不能把调试台词/自动运行一起带到成品。

## Core 双入口与变种

- **InstanceMode**：单例/Model 便捷访问，用于临时、调试、小场景；合理延迟查找和缓存，保留 Release，不要求普通使用者先注册/注销。
- **PrefabMode**：显式放置或实例化具体实现，适合主要场景、常驻模块、编辑态查看与调参。调用业务持显式引用，不靠全局搜对象隐去所有权。
- 通常支持两者但复用能力，不复制算法；特殊模块按实际需要。不要触发单例 getter 再造第二个常驻对象。
- 成品挂具体派生脚本，不把 Base 当成品。变种目录代表皮肤/实现，不把轨数、外形或 UI 年代写死成模块本质限制。
- 不预先承诺完全无单例依赖，也不擅自为了理论纯净强上 IoC/UPM。

## C#、Inspector 与文档

- 类型/方法/公开成员 PascalCase。长生命周期字段可用 `m_PascalCase`；保留既有一致的下划线风格，不无事批量改名。
- 序列化字段、GUID、数据键、公开 API、生命周期和兼容拼写不可只为风格更改；确需迁移须有授权与兼容验证。
- Inspector 可编辑字段必须有简洁中文 `Tooltip`；`Header`/`Range`/`Min` 不替代说明。私有/受保护字段加 `[SerializeField]`，外部只读时提供只读属性。
- 对外说明和有维护价值的 XML 写“为什么、时序、生命周期、边界”，不堆逐句翻译。新源码注释采用实际提供方标记，不冒写人类名。
- P1/P2 等计划编号不是永久业务术语。若保留，每个相关 class 头部 XML 就地定义含义及计划名称/日期/版本，不能仅扔 README 链接或猜编号意义。
- 保护准确旧注释、人工标记和 `[debug]`。确认失实且在授权范围的普通注释可换为有归属的新解释；不要改写人工注释后假装仍由人类写。
- 使用参数化共用逻辑、原子 API、小数据类型，避免成对“先检查再确认”的竞争窗口。退订事件、停止协程/计时器、释放对象应有对应生命周期。
- 显式标出时间、输入、音频、动画等关键顺序；Editor 诊断适当放 `#if UNITY_EDITOR`，必要运行告警保留。

## 修改、迁移与验证

先捕获 Git 分支/HEAD/脏状态，读取相关 Base/配对接口、活跃实现和 Core 索引链。附近侦察只看请求所需的邻接文件；范围外重要问题合并简报，不把原任务变成全仓治理。

历史项目是行为和素材参考，不是架构目的地。先找现行入口，迁移缺失能力，不用旧代码覆盖更成熟的实现；记录来源、依赖与省略项，先最小 Demo 再业务接入。保护手工内容、玩家数据和未保存的 Unity 现场。Unity 场景/预制件通过合法 Editor 工作流调整，不直接手改 YAML。

`.cs` 先过含 Editor 路径的语法检查，依赖缺失单列；随后项目编译、场景/样例运行和功能体验按层验收。截图、听音、交互、实例唯一性等需各自真实证据，不能用对象存在或自动跑分代替。没有可用检查器/Editor 就明确缺口，不假绿。
