# 写给项目读者的 Issue 和根 README

## 新建 Issue

AI 在任一项目新建 Issue 前，先看项目已有的贡献说明、模板、标题、优先级和标签，再查重。沿用项目的语言和约定。项目缺少规则时，采用下面的最小约定，权限和任务范围允许时补齐必要分类。

标题用 `[优先级][项目类型] 一句普通读者能懂的话`。一条标题说一件事，让读者知道哪里发生什么、希望怎样；保留必要专名。把类名、编号、散列、精确路径放在正文，用状态字段表示进度。正文先说明现象、期望和影响，再给最短复现、版本、证据或验收条件。

| 缺省优先级 | 如何选择 |
| --- | --- |
| P0 | 需要立即处理的严重阻断或重大损失，例如正在丢失数据。 |
| P1 | 核心流程受阻，影响较大，缺少可行替代。 |
| P2 | 一般问题或已有可行绕行的改进。 |
| P3 | 可以延后的规划或低影响优化。 |

例如，保存是核心流程且无绕行时，写「[P1][保存] 点一次保存却生成两份记录」，正文再给重复请求的版本及复现步骤。类型取项目使用的功能或问题分类，如保存、联机、规划。相同症状的优先级要结合影响人数、紧迫性和替代方式判断。

提交前查看现有 labels 的名称、含义和颜色，按价值与性质追加能帮人筛选的分类，保留原有标签。红色 bug 只在项目这样定义且确实是缺陷时使用，名称本身也应能说明含义。缺必要分类可建立一个语义清楚的彩色标签。避免同义标签、为每段标题机械加标签或全仓改色。历史 Issue 的标题只在人工明确要求时修正，不批量追改。

## 根 README

让第一次来的人从首页就能判断项目是什么、给谁用、能做什么、为什么值得用。选一个读者熟悉的使用场景，展示实际效果或能复用的范例。快速开始给出必要前提、最短可执行的安装、部署或使用步骤，以及判断成功的方法。资料类项目可以直接带人找到第一份可用资料。导航只指向实际维护的入口，深入的手册、配置与开发资料放到相应页面。

先读现有首页及它承担的项目职责，保留可用的命令、示例、限制、来源和共享记忆索引。按读者真正需要看懂的关系选择代码前后对照、可复制示例、表格、流程图或图片。标明示意、实测环境和已知限制。已有 logo 可沿用，版本、许可、平台、CI 徽章都要有真实依据。公开配图按[截图与访问核查](commit.md#截图与访问核查)办理。

参考图只提供信息组织的骨架。项目定位、框架和读者决定配色、版式与视觉风格。公开仓缺多语言时补一个读者能用的 English 入口与必要的英文 README，保留默认语言并双向导航。已有多语言沿用其入口，本次范围有翻译要求才扩写。根 README 同时承担模块入口时，继续遵守[目录共享上下文](directory-context.md)的责任区与持久资料要求。
