# 在哪条分支开发，什么时候可以合并

本页说明开工前谁选分支、两次合并请求分别交付什么。遵循用户当前明确决定和项目已声明的分支约定。技能源码仓库的 `main` 是在线发布通道，日常开发走分支和 PR，保持 `main` 可安装。技术判据见[合并请求的技术审查](../SKILL.md#合并请求的技术审查)。

## 在发布分支动手前

1. 先核当前分支、HEAD、工作区和暂存区，并对照远端分支确认哪些提交尚未推送。没有跟踪分支或无法核实远端时说明未知项。在 `main`、`master`、`release` 等实际承担发布或集成的主分支上，即使是小修，也先询问用户是否新建分支。根据实验性、对发布通道的影响、改动范围与回滚成本给出建议。
2. 无论当前在哪条分支，发现未提交改动或未推送提交，先列出涉及的文件或提交，让用户决定去向。给出三种选择：**带到新分支**、**先推送到当前分支**、**先验收，再切到新分支**。说清每种选择会带走或推送哪些内容，尤其是与其他任务混在一起的改动。保留本地改动，禁止擅自 `stash`、`reset`、丢弃文件、强推或重写已发布历史。
3. 答复前可以继续只读调查与拟定方案，切分支、改文件、提交或推送等写操作等待答复。在任务或关联 Issue/PR 记下询问与用户决定。用户已明确指定本次分支或处理方式时直接按答复执行，尚未交代的去向仍要问。明确要求本次留在主分支的决定只对本次有效。

## 分支类型与命名

按内容推荐类型，用户有决定时以用户为准。在 Issue 或 PR 中写明类型、作者短标识、分支名与签出点（建分支时的提交 SHA），便于后来还原审查范围。

| 类型 | 用途 |
| --- | --- |
| `fix` | 修复或优化已有功能。 |
| `feature` | 新增功能，也包括实验功能。 |
| `archive` | 归档已完成或已放弃的工作。 |
| `legacy` | 保留继承的项目原始分支、档案存根，或特大缺陷修复后仍可参考的遗留分支。 |
| `bak` | 临时或定期备份。 |

新建分支默认用 `<作者短标识>-<内容简述>-<动作或日期>`，全小写，以短横线连接。作者使用固定短标识，末段用动作词（如 `add`、`fix`）或六位日期 `YYMMDD`。例如 `ld-blueprint-add` 表示 LD 新增蓝图功能，`ld-fishnet-261111` 表示 LD 在 2026-11-11 变动 FishNet。日期取分支实际建立或变动的日期，不从提交时间倒推。

类型是否写进分支名前缀仍待用户决定。历史上的 `feat/`、`fix/`、`docs/` 保留原名，新分支已有项目命名要求时遵循项目要求。新约定只用于此后新建的分支，不重命名历史分支。

## 第一次请求合并

第一次只提交 Issue 和 PR 审查材料，**不合并**。

- 明确分支签出点和源分支最新推送的提交 SHA。沿两点之间的全部提交核对改动，包括中间引入后又撤销的内容。只看最后一个提交或最终 diff 会漏掉这些经过。若缺少签出点或不能确认最新推送，先核分支创建记录或向维护者确认，在材料中标明缺口。
- Issue 写清要解决的问题和边界。PR 关联该 Issue，列出签出点、已推送到的提交、期间改动、实际验证结果、未覆盖项和兼容性影响。已有对应的 Issue 或 PR 可以补齐材料并互链，无需重复建单。提交给审查者，按[合并请求的技术审查](../SKILL.md#合并请求的技术审查)留下结论和缺口。

## 第二次请求合并

用户再次明确请求合并时，先核对对应 Issue、PR 和已提交的审查记录，确认覆盖当前待合并提交。缺 Issue、缺 PR 说明或审查、验证边界不清，或者审查后又推送了改动，都要先补齐对应材料与审查，期间不合并。材料齐全、技术缺口已处理且有人类合并授权，才按项目的执行流程处理冲突与合并。若冲突处理改变了已审内容，对受影响部分补审、补验。

## 合并之后

核相关 Issue 和 PR 的实际状态。已解决的酌情关闭，遗留事项写清还缺什么、在哪个 Issue 或 PR 继续跟进。按影响范围在实际合并版本重跑相关流程，记录被测提交、结果及未验项。分支上已通过的结果只对当时的版本有效。回归入口见[推送后与合并后的回归](directory-context.md#推送后与合并后的回归)。
