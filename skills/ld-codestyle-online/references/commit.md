# 提交与真实交付

```text
##模型：bot名称（若有） + 模型具体型号 | 本次具体改动短摘要
##问题：实际症状、需求缺口或根因及影响范围。
##解决：改了什么、为何这样改；验证结果及未验证的边界。
```

- 三段按顺序，使用全角冒号，中文正文；必要命令、API、路径和实际模型标识保持原样。
- Bot 存在就写真实名字；没有则仅省略 Bot。不能用 `AI`、提供商品牌、`Codex` 或 Bot 名字代替精确型号，也不把审查者身份记成实现者。
- 首行必须有 ` | ` 后的具体摘要，Git 列表应能辨认每次业务变化。不得为了规范重写已公开历史。
- 测试、文件范围、风险、未验部分放解决节；混合贡献说明已知归属，不凭 Git author 猜人工/AI 比例。
- 不用空泛“优化一下”，不以 `fix:`/厂商前缀替代该格式。源码注释前缀与提交身份是两套不同约定。

## 提交前

1. 核本次任务有提交/推送权限，当前分支和远端是目标；只暂存授权文件，不为清空工作区而混入人工未完成内容。
2. 人类标记新增/修改默认阻断 AI 提交；只有人类明确确认其真实亲写并要求混合提交才例外，AI 不再改动这些行。保护历史 `LD:`、自定义人工标记和 `[debug]`。
3. 核配对接口与 Base 扩展点、XML 文档、命名空间、插件隔离、Inspector Tooltip、模块索引、序列化/GUID 和兼容边界。
4. `.cs` 改动过含 Editor 路径的语法检查；缺引用不冒充语法错误，也不冒充编译成功。运行时、Unity 编译、Play、视听体验分别报告真实结果。
5. 读 staged diff 和最终首行；提交后回读 commit，获准推送后回读精确远端 SHA。不得强推、自动 stash/reset/clean 或改写旧提交解决普通问题。

## 示例（结构示意，不是已经发生的验证）

```text
##模型：<实际Bot名> + <实际模型标识> | 修复模块重复实例化
##问题：常驻预制件已存在时，便捷入口仍创建了第二份实例。
##解决：让便捷入口复用当前已绑定实例，并保留显式创建路径。
验证：填写真实执行结果；未做的 Unity/画面验收明确列出。
```

派协作任务以最新可证基线创建独立分支，避免多写者覆盖；普通合并保持真实模型/作者说明。报告完成时以人类验收目标为中心，不能用测试数量或文档数量替代功能可用。
