# 合并请求的技术审查

采用本技能的项目，代码层面的技术判定默认归本技能管。人类当前明确指令优先，其次是项目 `AGENTS.md` 和区域 `README.md` 的约定，其余按本技能默认规则。项目可自行规定参与者是否必须安装技能。未安装的审查者也按项目采用的同一份公开判据审查，安装状态不改变结论。

1. **确定影响范围。** 从此次改动的真实入口沿调用链核直接依赖与受影响调用者。顺带发现的无关问题单列一句，技术结论仅针对本次影响范围，无需全仓审计。见[修改、迁移与验证](contract.md#修改迁移与验证)。
2. **核对适用的原判据。** 按项目采用范围逐项查原文。
   - 对照[模块结构与控制边界](contract.md#模块结构与控制边界)和[插件改写约定](contract.md#插件纯净与必要改写)，检查配对接口、Base 扩展面、命名空间与插件边界。遇到超出授权、需要裁决的接口或 Base 变更，将该项交给人类或项目已授权的架构负责人。
   - 对照[序列化与 Inspector 暴露面](contract.md#cinspector-与文档)核变更的必要性与兼容性。按[强制注释验收](comments.md#执行委派与提交验收)检查改动函数的有效头部文档和核心原理旁的行注释，按[代码格式整理](contract.md#代码格式整理)检查是否只整理改动范围。
   - 触及共享记忆时按[读取、更新和权限](directory-context.md#读取更新和权限)核真实增量和旧正文保全。按[提交消息的格式](commit.md#格式与工具)核提交及贡献归属，不能把审查者记成实现者。
3. **亲自运行项目已有且适用的门禁。** 在待审提交上实跑语法检查、项目编译、测试和文档契约测试，按影响范围实测可运行入口及实际效果。不能凭作者自述签字放行。分别记录被测提交、运行结果、未验项及原因，编译通过不能代替效果验收。
4. **给出技术结论和缺口清单。** 写明哪条判据受影响、证据在哪、还需谁裁决。审查默认只出意见，不顺手改作者代码。确需修改时，在授权范围内另起改动，用自己的提交身份署名。自审不算独立复审，技术通过仅回答该版本是否满足适用判据。是否合并由人决定。合并动作、快进或压缩等方式，以及合并前后如何读回核验，归执行侧发布与流程规范。何时提交材料、何时可考虑合并见[分支与两次合并请求](branch-workflow.md)。

本节暂定。遇到判据分歧，先在本项目的 PR/Issue 或所属区域记忆里保留原审查、分歧和处理依据。通用经验经脱敏并获授权对外分享后，在[审查规则议题 #27](https://github.com/LastDreamTeam/LDAI_CodeStyleAgentSkill/issues/27)追加可公开的案例与依据，保留原文。私有项目记录留在原可见范围内。上游根据实际案例补充入口，判据仍在各自原章节维护。
